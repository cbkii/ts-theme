New car-start code must use a separate PR stacked on that branch; recheck its exact head before starting. Repository instructions are persistent guardrails, not proof a proposed feature exists.
- **Release blocker:** The owner reports that the PR #17 TESTING candidate repeatedly fails genuine cold readiness for Music, Radio and Maps across available diagnostic profiles. Treat this as a P1 physical observation; the earliest failing layer for each source is not yet captured. Green CI and signed APK publication do not overturn this, and no reboot/cold boot/ACC acceptance is claimed.
- **Requested next outcome (not implemented by this documentation change):** On genuine Android boot and supported vehicle ACC wake, ts-theme should automatically prepare Auxio-TS, NavRadio+ and Organic Maps together, so one ordinary HOME Play controls each audio source and an interactive compact Maps view is available without separately opening the apps. Restore readiness after launcher/source loss. No startup audio, source switching, focus theft or protected UI disruption. These behaviours require code, exact-device contracts and physical qualification; see [automatic car-start readiness handoff](docs/AUTOMATIC_CAR_START_READINESS_PLAN.md).
- **Execution order:** repair explicit source-app icon delivery independent of failing Maps; implement a small application-owned, single-flight, source-specific readiness coordinator; qualify actual service/browser/queue/tuner/map readiness; try one genuinely different, controlled Activity/bootstrap method only when necessary; then consider a loader. Compare methods, not repeated identical root attempts.
- **Current vs authorised design:** PR #17 is background-only for source readiness; it has no full car-start coordinator, launcher boot receiver or working source-Activity priming. This policy may be deliberately revised for the requested implementation, but only through narrowly scoped, reversible, owner-authorised, physically gated foreground staging. Do not add hidden foreground launching as an unqualified default.
- **Tests/artefacts:** Preserve PR #15's bounded, read-only 1.3 diagnostics and PR #17's beginner-friendly P/F/N guided smoke/screening kit. Update the kit only when corresponding code changes exist. Only a newly signed, final-head TESTING APK with matching hashes can enter physical qualification. Run the three-source car-start smoke gate before long validation.
- **Efficiency:** Inspect only relevant original source and contrary evidence; prefer one read-only discriminating test before uncertain mutation. Implement the smallest coherent change in its owning repo, write deterministic regression tests and report unrun physical gates as NOT_RUN. Do not merge or install production changes without explicit instruction.

- Target CB's exact Topway TS18 first: Android 10/API 29, physical 1280 x 720. Present exact-device evidence outranks historical assumptions.
- **Local/offline/private by default** is repository policy. Core HOME operation must not require Internet access. **No analytics** are added by default: do not add remote analytics, tracking, cloud telemetry, remote configuration or automatic upload of diagnostic/user-behaviour data. Diagnostics stay bounded, local/exportable and user-controlled.
- The standalone launcher (`com.cbkii.ts18launcher`, module `launcher/`) is the **only product** of this repository. The DoFun/RePlugin theme module, its RePlugin fetch, theme installers and theme release path are **retired and removed**; `tools/ts18_theme.py validate` fails if `:theme` or retired paths return. The installed OEM `com.dofun.variety` host is unrelated to that deletion: never uninstall, disable, clear or alter it; it remains the device's HOME fallback.
- Never build or publish `launcher.variety.theme.plugin.sfp_cbk_black` from this repository again, and never reuse it as a launcher identity. Historical theme releases/tags stay untouched.
- Preserve the TS18 SystemUI safe area. The historical conservative raw safe-right is x=1225, but later device evidence measured about x=1227 with a 53 px right bar; top/right bars and density overrides are runtime-sensitive, not immutable constants. Use the current Activity/decor/inset geometry without double subtraction. Preserve the 96 px rail and 88 px media strip and never render/touch into the live protected SystemUI region.
- Responsive behaviour is exact-device/known-landscape only: physical 1280x720, decor-fitted bounds, and the Topway right-sidebar shown/hidden profile when evidence supports it. Do not turn HOME into a generic split-screen/phone/tablet responsive launcher.
- Preserve the continuous top-strip structure `[Radio controls] [shared active metadata] [Music controls] [DD MMM]` (Radio/Music groups may swap sides by user preference). DD MMM is display-only, transparent and compact; it is not a Settings shortcut.
- Source hierarchy is asymmetric but both sources stay actionable: selected Radio/Music gets the stronger semantic accent treatment; the inactive source retains a subtle accent cue/gradient and must never look disabled. Use restrained tonal gradients rather than extra chrome/shadows.
- Keep HOME driver-facing controls icon-first and glanceable: use the pinned local Material Symbols Rounded family for fixed/override glyphs, stable transport positions, large touch regions, visible focus/pressed/selected feedback and restrained black/charcoal surfaces. Orange is the default semantic accent, but the bounded Material-derived accent-hue preference may recolour accent-role elements only. Keep physical TS18 safe coordinates in raw pixels but inner icon/text/padding dimensions in semantic resources.
- HOME rail order is fixed as Apps at top, optional 3-6 configurable quick slots in the middle, Navigation fixed at bottom. Quick 1 defaults to Settings. When HOME shortcuts are enabled, visible slots should divide the available middle rail space according to active count rather than being permanently packed for six. The whole HOME-shortcuts section can be disabled; when disabled, hide its count/editor settings too. Navigation remains at the bottom.
- Each HOME/drawer quick slot has separate App and Icon semantics. App controls actual package/role authority. Icon is `Auto` or a visual-only curated Material Symbols Rounded override and must never change what launches. Auto shows the real installed-app icon for explicit app shortcuts and the semantic role icon for role shortcuts. Settings previews must follow the same truthful identity rule.
- Accent selection is deliberately bounded and simple: use the Material-derived palette only and present it as a compact strip of colour circles. Do not add an arbitrary HSV picker unless later evidence establishes a real need.
- Setup is a short, skippable, repeatable checklist (`SetupActivity`), not a blocking wizard. The owner authorised it in November 2026. It is offered once, after Home is already usable, and only on a genuinely new install with no apps chosen. It is repeatable from Settings. It never takes Home or grants access silently: Home goes through the system role/Home screen, notification access through Android Settings, and the root listener grant stays an informed opt-in switch.
- The in-HOME app drawer may use installed application icons for application identity. Keep the five-column grid, five configurable quick-access slots and local app search with a visible voice-search action, without introducing a background indexer or remote service unless physical evidence justifies it.
- Keep the base launcher small and event-driven. Prefer platform Android Views/Java and ordinary framework APIs. Do not add Compose, AppCompat, Material runtime, Room, DataStore, RxJava, DI frameworks, image loaders or general-purpose Android networking stacks without a measured requirement.
- **The in-HOME Leaflet/WebView online map is retired.** Its classes, assets, build-time fetch and INTERNET/network-state permissions are removed; do not reintroduce a launcher-owned map renderer, tile cache or WebView. A previously stored/imported `leaflet` surface or `map.enabled=true` is upgrade input only and resolves to explicit **Fullscreen**; `raw_freeform` still resolves to `native_window`. `HomeNavigationSurfacePolicy` is the sole surface authority.
- PR #10's experimental Leaflet work is not the owner of navigation replacement. PR #14/#16/#17 already implement launcher-owned native Organic Maps task/window/recovery strategies. Preserve the existing controller's task/claim/focus authority and refine it there; do not revive speculative DoFun embedding or PiP alternatives.
- Network availability is optional and the launcher declares no network permission: core HOME operation must start and remain usable without Internet access. Offline-capable navigation/media apps are recommendations, never launcher dependencies.
- Organic Maps remains the preferred offline navigation authority. `docs/ORGANIC_MAPS_MODES.md` records exact current fork location modes as future integration targets only. Do not call private/JNI mode APIs cross-package, reflect into Organic Maps, inject root input, invent broadcasts or assume arbitrary Activity embedding.
- The launcher is not a GNSS requester. Its only location use is a read-only last-known position for the offline radio-region lookup when permission is already granted. Do not hold wake locks or run periodic background GPS/network polling.
- Generic music uses one selected Android MediaSession authority obtained through notification-listener access or the same real token obtained by a qualified MediaBrowser bind. Deduplicate by session token, watch membership/callbacks and retain the event-triggered defensive refresh throttled to a 15-second minimum spacing. On this exact unit `com.tw.media` is Auxio-TS; do not treat that package as stock Topway evidence.
- Radio is a separate authority. NavRadio+ (`com.navimods.radio`) is a third-party app, not stock Topway evidence. A configured radio app may be observed/controlled through its own MediaSession when available, but never synthesize a radio MediaSession or broadcast commands blindly across several paths.
- Driver-facing Radio/Music Previous/Play-Pause/Next controls remain enabled, use exactly one source-owned MediaSession/controller and never invent another player or blindly dispatch across methods. **Current PR #17:** controls are background-only; source icons are explicit foreground requests. Auxio binds its exported MediaBrowser and may use advertised PREPARE (not guaranteed queue/USB readiness); rejected root Auxio `startservice` stays disabled; future code must not retry the rejected Auxio root `startservice` route. NavRadio has an interactive exported-service path, not qualified passive warm-up; stock TW Radio has no declared service. **Authorised next work:** source-specific, bounded foreground Activity staging may prepare a source without auto-Play, followed by exact HOME task restoration, only after safety/authority checks and specific tests. A source icon must not be gated indefinitely behind navigation recovery.
- Current optional HOME-start media warm-up is bounded to qualified background adapters and storage-triggered Auxio reconciliation, not full boot/ACC readiness. Implement the requested application-owned coordinator for genuine boot, HOME, sleep/wake and source-loss events with one in-flight admission per source and automatic recovery. Treat `BOOT_COMPLETED`, screen interactive state and actual Topway ACC as **different** triggers; do not assume screen-on proves ACC. Passive NavRadio startup remains OFF until its installed version proves non-disruptive; preserve a user-disableable preparation option.
- Preparing a non-playing Radio/Music source must not interrupt the genuinely playing opposite source. Nominate the opposite source during preparation, but pause it only after the requested source has acknowledged Play. Do not make the launcher an audio-focus owner.
- Resolve Play/Pause intent once at tap time. Keep one bounded in-flight preparation per source, coalesce duplicate pending Play/Pause intents, preserve one monotonic deadline across root/normal/session fallbacks, and distinguish command dispatch from directional playback acknowledgement. A service start/browser token is not automatically READY.
- Exact stock TW Radio `com.tw.radio` bytes declare no Android service component. Its current path is existing-session/external-route only; do not invent a service or private Topway command. Any future authorised RadioActivity bootstrap needs exact-component/user and non-disruption qualification, never blind hidden launch. NavRadio+ Media3 service use must resolve against the *installed* API29-compatible package, not the newer reference APK. Topway source/tuner/DSP authority remains separate from Android MediaSession.
- Masked source-Activity priming is **not implemented or qualified in PR #17**. For the newly authorised cold-start work, first qualify normal Activity staging and exact-task HOME restoration; an optional `TYPE_APPLICATION_OVERLAY` loader may be added only after proper app-op/window verification and evidence of benefit. A loader never proves readiness or covers/intercepts permission flows, reverse camera, phone calls or critical SystemUI. Fail open to a truthful visible screen; never claim vehicle-window authority.
- Keep Topway/vehicle integration behind a narrow adapter. Public Android/package paths come first. Add private Topway binder/property/broadcast/MCU behaviour only from exact recovered contracts and keep failures fail-open.
- DoFun, TWCore, stock radio/music/Bluetooth, SystemUI, vehicle services and updaters remain protected. Replacing HOME does not grant their signature/UID/SELinux authority.
- Magisk-root may support bounded, evidenced source-specific service admission and exact-task/window operations as already implemented, plus setup/diagnostics; it never confers platform signing, UID 1000, protected SELinux, MCU/CAN authority or safe partition writes. An optional boot companion requires its own evidence, fail-open gating and recovery; do not add a persistent polling daemon or redundant boot writer.
- Never automatically clear DoFun data, set SELinux permissive, broadly chmod/chown, delete protected packages or write `/system`/`vendor`. DoFun remains enabled as recovery HOME during qualification.
- For a new install, stage ordinary launcher Activity first and enable HOME alias only after explicit user action. The exact unit has previously resolved `com.cbkii.ts18launcher/.HomeAlias` as HOME; recheck the *current* HOME before launch/focus/rollback work and preserve it unless explicitly changed. Keep DoFun enabled as a recoverable fallback.
- `scripts/termux/collect-window-media-evidence.sh` and `scripts/termux/collect-fast-media-evidence.sh` are read-only. They may read root-private launcher preferences/process context when authorised, but must not change settings, tasks, packages, playback or window state. Bounded/blocked captures are BLOCKED/UNVERIFIED rather than evidence of absence.
- Reverse-camera hand-off/return is roadmapped physical validation, not current launcher functionality. Do not add reverse-camera handling without exact evidence.
- Steering-wheel controls remain owned by the existing native system path. Do not add launcher interception unless exact evidence identifies a concrete unhandled event/regression.
- Vehicle telemetry is very-low-priority roadmap only; do not add persistent OBD/MCU/CAN widgets to the current launcher.
- Before changing typography/icon/touch geometry again, capture exact TS18 `wm size`, `wm density`, `densityDpi` and relevant display metrics. Do not claim the current raw-pixel interaction targets equal the intended dp targets until physically verified.
- Do not claim native radio/music, Bluetooth, projection, steering-key, reboot, cold-boot, reverse-camera or ACC behaviour passed unless physically exercised. Service/session admission, usable source readiness, Maps Activity/task/window/pixels/touch and audible output are separate acceptance boundaries; collect the earliest causal failure and mark blocked dependants BLOCKED.

PR #15's diagnostics and PR #17's guided validation are intentionally read-only collectors; do not silently make capture or P/F/N menu selection install, launch, Play, alter tasks or change settings.

## Media engines (November 2026)

`docs/MEDIA.md` is the current contract and supersedes older single-engine wording above.
Music and Radio each use exactly one engine through `MediaFeatureFacade`: **M1 Legacy** (default
and rollback; the original bootstrapper/monitor/listener machinery, left behaviourally unchanged)
or **M2 Direct** (`media/direct`, opt-in TESTING). Keep them independent: `media/direct` must not
reference legacy classes, open an Activity, use root, create a session or request audio focus (its
only way to start a source is that app's own exported MediaBrowserService, on a Play tap), and
`media/` (the contract) must stay free of Android and launcher types. A deselected engine must not
command, prepare or publish for that source. Do not change a default engine without physical
qualification and owner approval. The root grant of the launcher's own notification listener is
explicit opt-in only and must never restore access the owner revoked.
